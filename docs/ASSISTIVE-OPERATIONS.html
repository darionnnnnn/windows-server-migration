開始操作

從可信的本輪版本目錄，以具備必要權限的 Windows PowerShell 5.1 或受驗 PowerShell 7 開啟入口。先選角色與工作區，同一作業沿用 PairId。HTML 只呼叫本機 PowerShell 核心，不能直接對遠端主機下指令。

.\Start-ServerMigration.ps1 -Role Source -Workspace C:\MigrationWorkspace
.\Start-ServerMigration.ps1 -Role Manager -Workspace C:\MigrationWorkspace
.\Start-ServerMigration.ps1 -Role Target -Workspace C:\MigrationWorkspace -PairId <配對識別碼>
# Server Core／無瀏覽器環境
.\Start-ServerMigration.ps1 -Action Menu -Role Target -Workspace C:\MigrationWorkspace

畫面上的「操作」選單會顯示動作名稱、所需欄位、影響與下一步。先預覽，填好 typed 欄位，再確認執行。物件欄位若要求 TrustedPath／TrustedSHA256，必須提供可信 JSON 檔及其實際 SHA256；不接受貼入 PowerShell 程式碼。密碼只輸入機密欄位，不放入草稿、Owner、Reason 或 Evidence。

長工作會取得 jobId；重新連線會找回同一工作。取消是提出取消要求，等待核心到安全邊界後確認；關閉頁面不代表已取消。重啟後未完成工作標為 Interrupted，保留 journal 並先檢查再修復。

來源端：盤點與保存

  1. 先盤點來源並匯出可信 inventory；必要時啟用 DeepDiscovery，補登不能可靠辨識的動態腳本、參數、外部服務、可攜軟體及設定檔。
  2. 用 AssistiveEnable 建立輔助選取。所有發現項目預設選取；取消選取只改意願，不會刪除已搬檔案。
  3. 確認 IIS 全域／階層設定、site／pool／application／virtual directory 及全部排程 XML、folder、principal、安全與多個 action。無法自動處理的內容保留人工待辦。
  4. 主封包只收來源 C 槽的核准業務檔案與精確控制材料；其他槽交給非 C 工具。IIS／排程指向 D、E 等槽仍須完整搬移，不能因此排除 workload。
  5. 核准後用 EstimatePackage、ExportPackage、CheckPackage。final 搬移須在共同停寫窗口產生 FreezeSource；保留 full base、delta、manifest、journal、backup 與設定原檔。

工具不搬 Windows 系統本體、不自動安裝軟體。Apache／nginx／Tomcat 等產品保留盤點、檔案及設定，提供人工處置，不宣稱有產品專用自動還原。

管理端：把選取變成可核准計畫

  1. 建立來源／目的配對、匯入兩端 inventory 與來源軟體目錄。核對來源版本、選用版本、目的端觀測版本，三者各自保留。
  2. 逐項 SpecReview → SaveSpecReview，確認檔案 scope、原路徑／生效路徑、帳號與 SID 映射、必要 metadata、required consumers、共享物件影響及人工責任。
  3. GeneralHost 的處置用 DispositionPreview／DispositionSubmit、RequirementReview／RequirementDecisionSubmit。Pending 仍是待處理；必需相依不能單靠改成 NotNeeded 解除。
  4. 確認獨立項目可單獨處理，必要相依仍成套核驗。選取不是 Include 核准；完成必要審阅後再 ApproveMigration。
  5. 交付封包、可信 hash、核准計畫、非 C transfer plan、必要來源原檔與 HTML 文件。工作負載全部在非 C 槽時，C 封包可只有控制材料，不需放入假業務檔案。

來源封存計畫不因目的端選用新版而修改。已開始的舊版本作業用原可信版本完成或受控回退；本輪新流程重新盤點、核准及建立基線，不直接轉換執行中的 state。

目的端：比較、等待或還原

  1. 全新安裝 Windows Server 可作初始比較基準，但第一次實際觀測標為 FirstObserved；工具不假造「只有 OS」的盤點證據。用 TargetSnapshot 更新目的端，再 PublishComparison。
  2. 用 SetSoftwareVersion 表示選用版本。預設沿用來源版本；軟體缺少時由使用者手動安裝，工具不保證只還原檔案就能使用。
  3. 選擇 WaitForInstall 會等待；RestoreNow 只允許已就緒的獨立選取項目還原，缺相依者列 DeferredSoftware／人工處置。每次安裝或改版後重新盤點、比較及產生 TargetReceipt。
  4. FilePlacementPreview 列出逐檔占用、檔案／目錄型別衝突、原路徑、生效路徑與 metadata 條件。原設定例如 C:\temp 預設保存原路徑；目的端已有文件時不合併、不覆寫，報告列出無法放置的原路徑／目標路徑與原因。不可為了清除衝突而清空 Windows 或產品共用目錄。
  5. 用 PreparationPreview 取得目前選取與 chosen version 所對應的 RequirementId、ContextHash。負責人實際確認必要環境後，PreparationEvidence 填 evidence 檔／hash、Owner、觀測與到期 UTC，並明確 AckContextReadback。產出的可信證據檔再供 RestorePreview／Restore 等核心動作使用。
  6. 還原前先 RestorePreview，再 Restore，使用同一 manifest/hash、TargetReceipt/hash、target snapshot 與證據。寫入前核心重新檢查，版本或目的端變動會使相關證據失效。舊版證據不能當作新版已準備完成。

新版設定的「保存」與「生效」分開：找到舊設定不代表新版會自動讀取。需人工格式轉換或不透明脚本／Arguments 修改時，照報告逐項處理並提供實際驗證。

Windows 設定：先預覽再審閱

選 WindowsSettingsPreviewExport，輸入兩端 inventory 實際檔案路徑／hash 與 ReviewWindowsSettings。預覽產生受保護的 JSON 及安全的逐項差異表。工作卡的「使用此預覽準備設定審閱」將完整 SettingId 清單及來源／目的引用帶入 WindowsSettingsSubmit；PreviewHash 必須是 PreviewFileHash 的實際檔案 hash，不能使用語意 PreviewHash。

逐項选择 KeepTarget、External 或 ReviewedMigration，按要求填 Owner／Reason／Evidence；沒有合法預設時會留空。按鈕只準備表單，不代表核准或自動提交。ExpectedRevision 綁定預覽時的決策版本；他人修改後必須重新預覽，不能用新 revision 強行套用舊差異。機密設定值與原 XML 不直接顯示在工作卡。

非 C 槽與 IIS／排程成套還原

跳板機先用 NonCPeerProof／NonCPhysicalProof 證明兩端分享及實際目的端 state 身分，再 NonCPlan → NonCTransfer。各檔案驗 hash、必要權限／owner／時間／屬性與當輪 freeze；結果透過 NonCImport 匯入 Manager 權威狀態，之後 G 還原消費已驗證的非 C 結果，不能把它當 C payload 再抄一次。

來源 D→目的 C、來源 C→目的 D 都要核准映射及實際磁碟身分。C／非 C 使用同一目的實體資源 registry；別名、不同 Pair 或不同來源映到同一目的時不能各自繞過排他。缺磁碟、斷線、特殊語意未知、未驗 metadata 或錯誤 volume 只阻擋受影響範圍並列待辦。

IIS 与排程先以停止／停用方式建立，依 pool／folder 順序及 typed 設定還原並 readback。目標路徑映射必須傳入網站實體目錄與 task action／WorkingDirectory 等實際 consumer。opaque Arguments 不自動替換。未選 consumer 共用 pool、全域設定或 folder 的影響必須先確認。

結果、切換與可攜交接

  1. 用 ExportResult 記錄權威 state／journal 與逐項世代；實際目的端內容或 metadata 漂移會使有效路徑及完成狀態失效，歷史成功不代表現在有效。
  2. 同輪 final 資料、C／非 C 相依、必要 evidence 與 CutoverReady 核驗通過後，才 CutoverPlan／Cutover。啟用網站／排程是獨立核准動作；啟用後再由負責人供 BusinessFinal／FinalAccepted。
  3. AssistiveReport 產生完整 HTML bundle、逐檔衝突、原設定索引、軟體差異、人工清單及成套 workload 詳情。用 AssistiveReportCheck 的 DocumentManifestPath／DocumentManifestHash 檢查文件成員完整性。文件 manifest 與封包 manifest 是不同資料，不可互換。
  4. 交付時整個 bundle 一起帶走，用相對連結離線瀏覽；超過 2,000 筆仍提供完整清單，摘要數量需與實際完整資料一致。文件不是還原核准，也不是正式資格證明。

Owner 欄位記錄責任聲明，沒有企業身分驗證或權限委派功能。正式環境須由企業平台、產品與業務責任人核驗；合成測試不能解除正式 production gate。

失敗、續跑與環境探測

部分成功保留逐項 state、journal、原檔與 backup。先 CheckJournal／Repair；delta 要有可信完整 base，缺 base 的項目不能從不存在的目的端補檔。RollbackPreview 列出逐檔 undo 與漂移，再 Rollback；不移走未擁有的整個目錄、不刪人工新增檔案。非 C 資料的 undo 由其已證明的 transfer 邊界處理，不能借 C rollback 宣稱全數回復。

必要材料未結案、仍有 consumer／活躍工作或尚在回退期限時不得清理。CleanupPreview → Cleanup 必須核對新 revision、相依與明確確認；沒有保留期限／責任核准就保持原材料。請勿手動刪除比較基準、base、delta鏈、receipt、原證據、backup 或 journal。

沒有實機的項目用 EnvironmentProbe 匯出 HTML／JSON，再 ProbeImport 補入探測結果。HttpIntegrityProbe 檢查 loopback 回應與本機靜態資源實際 bytes 是否一致；若企業代理、端點產品修改回應，結果為 ModifiedTransport／NotTested，不把它算橋接通過，也不自動修改企業 policy。Server Core 使用相同核心的文字選單／可信 OperationRequest 備援。

目前小範圍測試只能證明所涵蓋的檔案、契約及 fixture 行為。實機 Windows Server、IIS／排程服務、SMB、特殊檔案、實際帳號存取、業務效能及正式資格以探測與企業補驗結果為準。

Keep the states distinct

Discovered means the source inventory saw an item. Selected records the operator’s current intent. Include / Exclude is a separate review decision. Approval seals an exact plan. A target receipt binds an exact package, generation, target snapshot and selected subset. A target journal records writes and readback. Owners then supply business validation. None of these states implies the next one.

Roles and handoffs

Source owner

Confirms the workload and its consumers, identifies the files and settings that matter, reviews source-path scope, and supplies an agreed freeze window. The source owner does not infer target readiness from source discovery.

Migration manager

Reviews all discovered records, selections, dependencies, mappings, software differences, manual tasks and approvals. The manager provides the portable report and retained evidence to the target team.

Target operator and business owner

The target operator captures a target baseline, checks conflicts, prepares selected software, chooses a bounded restore subset and inspects readback. The business owner tests the application, approves cutover and owns source retirement acceptance.

An Owner field is a responsibility declaration. It does not authenticate a person or prove enterprise authorization.

End-to-end journey

  1. DiscoverCapture an immutable source inventory. The first observed target snapshot is labelled as an observation; it is not assumed to be a pristine server.
  2. Select and reviewNew discoveries start selected. Change intent explicitly when needed. Review decisions and reasons remain separate from selection.
  3. Prepare the planMap exact file scopes and typed workload settings, identify shared consumers, record owners, and resolve prerequisites for the selected Include set.
  4. Approve and sealApproval applies to exact plan bytes. Changing a relevant selection, decision, path or setting requires a fresh review and approval.
  5. Observe target and compareCollect the target’s current software and workload inventory. Review source, chosen and observed versions, configuration and environment differences.
  6. Decide and restoreCreate a target decision for the exact package generation and allowed subset. A “wait” choice causes no writes. Restore reports partial, deferred, conflict and failed items separately.
  7. Validate and hand overInspect target-owned journal/readback, complete owner and business checks, record cutover evidence, observe the agreed period and handle source retirement as a separate accepted gate.

Source operator

Before inventory

  • Confirm the source host identity and the Windows Server role is within scope: general web, scheduled workloads and their supporting services.
  • Run the supported local PowerShell inventory path with sufficient read permissions. Record incomplete coverage and access failures for follow-up.
  • Keep original settings in the protected workspace. Public reports and draft screens must not expose raw XML, task arguments, credentials or private keys.

Before sealing

  • Review selected items, Include/Exclude decisions, required dependencies and shared consumers.
  • For source files, select an explicit whole-scope or reviewed exact-file set. The main package covers approved source C: content. Non-C content follows its separately evidenced D-channel path.
  • Confirm the source-volume/channel rule at the source host, then agree who will stop writes and how the final consistency window is verified.

A discovery suggestion that a path is on C: is not proof. The source-side capture and seal process must establish the physical source scope. Do not fabricate a C: file just because a workload has no C: data.

Migration manager review

Use the HTML review to examine the complete discovery set, including unsupported or opaque items. Each item should have a clear disposition, owner and reason where required. An unselected pending item need not block an independent selected workload, but a required dependency or shared-resource impact must be resolved for the selected consumer.

Compare before choosing

The software table separates source version, chosen target version, first-observed baseline and current observed target version. A saved comparison is useful only while its source hash, target hash and selection revision still match. Refresh and republish after those inputs change.

Preserve review history

Keep old evidence for audit and recovery. When a source selection, software choice or relevant mapping changes, do not reuse a stale comparison or target receipt. Re-review the affected scope and create a new exact decision.

Schema 3 is an explicit opt-in. Existing schema 1/2 catalogs remain readable under their compatibility rules, but an already approved or executing legacy job cannot be silently promoted into the Assistive state model. Reconcile its ownership and use a fresh migration.

Target operator

  1. Run the target inventory on the intended machine and protect its exact snapshot bytes. The first observed target snapshot is a baseline label, not proof the server was empty or clean.
  2. Review current differences and required software. If the selected software is not ready, choose WaitForInstall; the result is deferred and no target writes should occur.
  3. When ready, create a target decision receipt bound to the Pair, sealed plan, manifest, generation, target snapshot, comparison revision, selection revision and selected subset. The subset can only be smaller than or equal to the approved Include set.
  4. Preview conflicts and workload readiness again immediately before writing. A pre-existing unowned target object or file is a conflict; it is not silently replaced.
  5. Run the restore through the supported operation path. Keep its durable state and journal with the target operator’s protected evidence. Reconnect to the same operation after interruption; do not launch a duplicate generation as a recovery shortcut.
  6. Review every per-item status and readback. Deferred, blocked, conflict, manual, reboot-required, failed and cancelled work must remain visible as such.

Software and version choices

Windows is based on the target operating system. For other products, the source version is a reference; the operator may select a different target version and install it through the organization’s approved process. The catalog must preserve source version, chosen version and observed target version as separate values.

Matching or newer is not proof of compatibility

Version equality or a newer version does not prove that a provider, architecture, account scope, license, runtime, configuration, file format or application behavior is compatible. Do not automatically rewrite data formats or convert configuration. Have the product and application owners validate their supported upgrade path.

When a product is missing, identify who installs it, the selected version, media/source, license and configuration prerequisites, and how installation will be verified. A read-only environment probe reports observations only; a passing probe is not a qualification, restore, security or business test.

Manual work should name its responsible owner, procedure, evidence needed and a next action. If the comparison changes after installation, recapture the target and publish a fresh comparison before relying on the result.

Show the exact original value, reviewed target value, field pointer and disposition. Opaque task arguments, scripts and unparsed settings remain manual; do not do global string replacement.

Exact-file selection is constrained to the approved file whitelist. Preserve the original path and bytes even when the target application uses a new location or format. A selected file being copied does not prove the target application uses it.

IIS and scheduled workloads

For a site, application, virtual directory, pool or task, review every discovered reference that affects the selected workload. The review should show all selected, unselected and unknown consumers of shared resources. A shared pool, task folder permission or global/section configuration can affect workloads beyond the item on screen.

  • IIS and task objects are staged disabled. A typed reviewed activation decision is separate from writing and readback.
  • Review source XML, mapped target values and activation intent as separate facts. Raw source XML belongs in protected evidence; HTML presents only the safe, typed projection.
  • Global and location-specific IIS section changes must be limited to the reviewed section and typed field changes. Unsupported node semantics or ambiguous collection identity require manual treatment.
  • Task actions, working directories, principals, triggers, settings and folder security must be reviewed as a whole. Opaque arguments are not safe to rewrite automatically.
  • Required files on non-C volumes stay in the workload scope and are handled through the separate D-channel result. They do not become C package entries.

All available non-IIS discoveries still need explicit treatment. This workflow does not add product-specific adapters for unsupported products.

Conflicts, deferred work and partial results

Existing target content is preserved by default. The report should identify the affected item and whether the issue is a direct filename collision, an occupied file-vs-directory path, an unowned native object, an unresolved consumer mapping or a broader scope block. Do not tell operators to empty Windows or shared product directories to clear a conflict.

DeferredSoftwareInstall or prepare the dependency, recapture, compare and decide again.
WaitForInstallAn explicit owner choice to wait. It is not a restore success.
BlockedConflictA target object/path is already present without exact ownership.
ManualEvidenceRequiredA named owner procedure or accepted evidence is still outstanding.
Failed / CancelledRetain the operation journal and inspect recovery guidance before retrying.
PartialSome independent items may be ready while others remain blocked or deferred.

Do not turn a green item count into an overall success percentage without showing the denominator and all remaining selected work. C and D outcomes, native object writes, manual preparation, business validation and cutover each have their own status.

Portable HTML report and evidence bundle

Export creates an offline index.html and an evidence/ folder. Open the HTML locally in a supported browser; relative links should continue working after the whole bundle is moved together. The protected JSON evidence copies are hash-verified and remain separate files; they are not embedded in the page.

The report indexes the immutable source snapshot, target baseline/current snapshots when present, software observations, selection and decision, comparison, migration paths and manual work, imported result references and target decision history. For each result it states what it proves and what it does not. Missing evidence remains “NotTested”, unknown or not recorded.

Raw XML, full settings, task arguments and secrets are excluded from the HTML projection. Treat the evidence directory as protected migration data: it can contain original inventory settings and must retain its access controls when copied or transferred. A hash detects changed bytes; by itself it does not authenticate who produced those bytes.

The manager report is not a target journal and does not reconstruct one. It does not itself approve a plan, establish target readback, accept business behavior, complete C/D transfer, authorize cutover or release the source.

Validation, cutover and source retirement

After restore, the target operator verifies exact-generation state and readback. The application owner checks real behavior, including identity, access, integrations, schedules, logs, monitoring, backup and recovery. Record the owner, evidence reference, time and generation that was actually tested.

Cutover has its own readiness and execution record. Keep the source available during the agreed observation window. Source retirement is a later, separate decision after post-cutover business and operational acceptance. A successful file hash, native API readback, installer observation or report export is not a substitute for that acceptance.

Production qualification applies to the tool and supported environment separately from a single isolated migration. Until external prerequisites and representative host/data evidence are accepted, report the qualification as NotTested or not established.

Troubleshooting and safe next steps

“The report says the target baseline is first observed.”

That is intentional. Capture and inspect a new current target inventory. Do not call it a clean baseline without independent evidence.

“My software version or settings changed after comparison.”

Refresh only after capturing trusted current target facts. Republish comparison and recreate any decision receipt whose bound hashes/revisions changed.

“A report link is broken or evidence fails its hash.”

Keep the bundle unchanged, verify that the entire directory was moved together, and reacquire the referenced evidence from the protected workspace. Do not edit the JSON to make its hash pass.

“A path or task argument is unresolved.”

Assign an owner to inspect the exact consumer and choose a safe target value. Keep the item manual until its typed mapping is reviewed and appears in the consuming setting.

“An operation was interrupted.”

Keep the same state directory, package, journal and generation. Inspect the durable operation and recovery preview before repair or retry; preserve ambiguous intent and backups.

“The file report is green, but the workload is not usable.”

File placement is only one gate. Check workload configuration, software, identity, networking, dependencies, runtime behavior and business acceptance independently.

This guide is an operator aid. Follow the approved change, security, evidence-retention and recovery procedures for the environment. The live catalog, sealed plan, target receipt and target journal remain the authorities for their respective states.
