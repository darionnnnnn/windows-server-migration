## 3. 使用流程與共同契約

### 3.1 舊主機備份

開始／確認這台電腦 → 選擇儲存位置與模式 → 掃描可備份內容 → 逐項決定（自動模式略過）→ 備份摘要與開始 → 備份進度 → 備份結果與交接。

- 一般步驟的本機權限／容量等必要檢查自動完成；與 G 的開發診斷分開，不能要求一般使用者先看完整技術報告。
- 預設逐項詢問，每頁呈現一個業務項目、用途、檔案位置、相關項目及「加入／不加入」。預設加入，排除可選白話原因並保存到現有核心決策，不要求自行寫 JSON。
- 自動模式文字：「自動加入所有可備份項目，不再逐項詢問」。只對本次工作有效；首次明確開始時說明範圍及輸出位置，完成掃描後可自動繼續已授權備份範圍，不再逐項確認。
- 自動模式不代填不存在的必要證據或核准。缺材料、權限、容量或核准時保存進度，顯示「需要處理」及一個下一步；不能靜默跳過後宣稱完整。
- 非 C 槽仍遵既有核准／跳板通道，不偷偷加入新的任意磁碟複製機制。需要另一台電腦作業時，精靈清楚停在交接步驟，可匯入結果後續作。

### 3.2 管理端交接

選擇要處理的搬移工作 → 讀入舊主機資料 → 確認新主機資料 → 查看差異與項目 → 必要審閱及核准 → 產生交付材料 → 交接結果。

路徑、已有材料識別碼、revision 等可從可信狀態取得的值由程式帶入；獨立可信雜湊／責任人證據等不能從不可信材料自行認定。必要人工輸入用具體說明及範例，不暴露整份巢狀參數表單。

### 3.3 新主機還原

開始／確認這台電腦 → 讀入備份材料 → 檢查新主機 → 選擇還原項目及軟體版本 → 顯示可還原與待處理內容 → 明確確認還原 → 結果與續作 → 驗證及另行確認啟用。

保留等待補裝／先還原具備條件內容、已核准內重選、原路徑保存、目的衝突不覆寫及逐項續作。還原完成不等於軟體可用或正式啟用完成。

### 3.4 導覽、狀態及名稱

- 左側基本入口：開始／繼續操作、使用說明、開發者環境探測；進階工具保持可到達但收合，不作正常旅程必要入口。
- 掃描成功含零項結果時顯示「掃描結果」；部分掃描有有效資料時也顯示並標示不完整。尚未有結果時不顯示；純失敗資訊留在當前步驟及作業紀錄。
- 備份已有持久結果紀錄（含失敗／取消／部分完成）才顯示「備份結果」，不能以按過開始或只有盤點資料判定。
- 結果與目前工作／主機／世代綁定；切換工作、直接網址、重新整理、過期資料都重查。其他工作舊結果不混入目前工作。
- 「角色」改「這台電腦的用途」；Source／Target／Manager 顯示「舊主機／新主機／整理搬移資料的電腦」。
- 「配對」改「這次要搬移的主機」，顯示舊主機 → 新主機及可辨識工作名稱；未知新主機明示尚未指定。內部識別碼留在詳細資訊，不變更既有核心身分語意。
- 狀態需區分尚未開始、處理中、需要處理、部分完成、完成、已取消、失敗。步驟進度不是備份覆蓋率；未知總量不得顯示假百分比。

## 5. 分段規格及驗收

### A：建立可靠的本機載入與錯誤路徑

範圍：HtmlConsole.ps1、AssistiveHttpProbe.ps1、啟動入口及既有 HTTP／瀏覽器測試。先記錄初始 HTML、CSS、JS、session API、後續 API 與長作業的實際回應，區分程式、傳輸差異、環境阻擋及測試替代路徑。修正可定位的程式錯誤，不預設停用或更改 AdGuard／代理／企業政策。

輸入：現有工具及隔離 workspace。輸出：能定位載入失敗的診斷、穩定 API 與明確錯誤／重試畫面，供 C/G 使用。

驗收：
- A01 本機隔離服務經真實瀏覽器載入 HTML／資源／session／資料，能完成一次讀取及安全測試操作；記錄實際使用原生橋接或測試橋接，不混稱。
- A02 模擬逾時、連線重設、非 JSON 回應、session 過期及內容變異，畫面停止無限載入，顯示白話處置與可追查識別碼；不重送未知結果的寫入。
- A03 若現有安全軟體環境確實無法由程式修復，驗收本輪可控的偵測、回復及隔離真瀏覽器流程；原始傳輸維持未通過紀錄，不把解除外部攔截列為門檻。這不是刪除 bug 工作：需留下重現、定位證據及已修正／外部限制的分類。

### B：整體排版與容易理解的頁面

範圍：src/ui/index.html、console.css、console.js 動態文案；所有一般表單、結果、錯誤及進階頁面同型問題一併檢查。主要正文 18px、主要按鈕至少 48 CSS px 高，按鈕群組至少 12px 間距；頂列高度隨內容調整，固定區域不遮焦點，文字與長路徑可換行。

輸入：既有頁面及狀態投影。輸出：一致的頁面／卡片／按鈕／步驟框架及白話名稱，供後續各精靈使用。

驗收：
- B01 真瀏覽器檢查 320／768／1280／1920px 寬、桌面 200% 縮放、長中文名稱及路徑；頁面本體無水平溢出，必要表格在自己的容器捲動，按鈕不交疊、文字不被裁切、框線連續且不穿過內容。
- B02 留存主要頁及錯誤狀態截圖，主代理實際檢視；DOM 尺寸檢查不能取代畫面確認。
- B03 Tab／Shift+Tab／Enter／Space 可走完整主流程，焦點可見且不被固定區域遮蔽；一般正文及操作文字實測對比至少 4.5:1，主要控制資訊至少 3:1。

### C：精靈狀態與可恢復作業

範圍：HTML projection／操作請求及既有核心狀態、console.js 導覽與 job 恢復。精靈為既有核心的編排與投影，不建立另一份互相矛盾的成功旗標。確定後端狀態版本、原子保存、舊資料缺欄位預設與未知版本拒絕方式。

保存工作識別、主機用途、目前步驟、掃描世代、已確認選擇、自動模式範圍及 operationId；秘密只留記憶體。頁面重新開啟須從權威狀態恢復，不依賴 browser localStorage 作唯一來源。前進／返回不等於重送工作，寫入使用既有 revision／CAS 及 idempotency。

驗收：
- C01 空工作、零項結果、部分結果、備份失敗／取消、有舊工作結果及直接網址，左側按鈕顯示與資料歸屬逐一符合 3.4。
- C02 保存後刷新、關頁重開、工具重啟皆能辨識目前步驟／作業結果；不保存秘密。崩潰前未確認的輸入不冒稱已保存。
- C03 雙分頁修改、掃描世代更新及上下文切換時，過期寫入被拒絕並保留可安全重看內容；不覆蓋另一個工作的決策。
- C04 連點下一步、提交後斷線再連線、取消後續作，測試實際核心操作次數及結果，無重複備份／還原。各頁均能看到持續作業狀態，不必進作業頁才更新。
- C05 載入第四輪 fixture／未知狀態資料：保留核心資料，不能推測已完成；不適用新精靈的舊工作提供白話回到原流程途徑。

### 9.1 自動處理的邊界與優先序

|---|---|---|

### 9.2 操作負擔的可檢查標準

- 一般成功旅程不要求輸入內部 ID、revision、JSON、collector 名稱或重複輸入已有可信的路徑／版本；外部可信材料仍需有真實信任來源。
- 逐項模式預設加入時，一次「下一步」即保存該項決策並前進，不額外要求「選加入→保存→確認→下一步」。排除後按下一步同樣保存，只有影響超出目前項目才顯示必要決策。
- 自動模式通過初始必要準備後，不出現逐項或無實質差異的重複確認；真正造成寫入／授權範圍變更的確認只保留一次，操作按鈕直說「開始備份」「開始還原」「確認啟用」。

- 詳細資料收合但不刪掉，頁面切換不要求重新填寫已保存項目；沒有變更時不重問。
- 首次發行入口要能以現有部署方式直接開啟正常 UI，無需先編輯 PowerShell 命令；若需提升權限，說明操作但不自行更改執行政策。無瀏覽器環境保留既有文字備援，不承諾在 Server Core 本機呈現 GUI。

## 11. 全專案回查與執行順序修正

### 11.1 從入口到結果的完整資料鏈

啟動／本機身分 → 用途及固定 workspace → 材料信任／工作綁定 → 掃描與分組 → 自動值及使用者決策 → 必要核准 → 實際封裝／非 C 交接 → 成果核驗 → 新主機匯入／重查 → 還原／續作 → 另行啟用 → 結果及交接。

每個箭頭均需檢查：輸入身分與版本、過期處理、重複請求、取消／崩潰恢復、下一端實際消費及白話呈現。G 是旁路診斷，不能寫回上述權威狀態；HTML／文字入口共用核心。步驟新增持久資料時遵循第 7 節版本相容及材料鎖，不另存一套完成真相。

### 11.2 依賴排序的補正

原順序將 E 放在 F 前，卻把 E 所需的目標身分／管理核准留在 F，存在開發依賴倒置。F 拆成 F0（既有管理準備及可信目標身分／核准的導引）與 F1（交接完成、目標還原及續作）；A–H 範圍不刪減。

建議順序改為：A → B → C → D → F0 → E → F1 → G → H。F0 不依賴 E 新產物，使用既有有效材料 fixture 驗證；E 真產物在 F1 做連續整合。G 仍只依賴 A/B/C，可獨立提前處理但不代表啟用平行代理。第 12 節若選獨立備份，需再評估這條資料鏈與提交邊界後定案。

### 11.3 驗收覆蓋及狀態更正

H01 的完整性清單擴充為原始七項需求、第 1／9 節定案、F01–F09、R01–R12、所有 A–H 及 R-A01–R-A12；兩份清單不能擇一。初次建置不能假設已有核准 fixture，必須另測空工作起步與前置缺口。

第 3.1 節流程是使用者導覽摘要，不代表免除管理準備。自動模式在初始準備完成後直接開始，逐項模式才有逐項確認及結束摘要；不得為保留舊流程而在自動模式再次加入無意義確認。

本次只做靜態程式核對、流程推演及規劃修訂。不能從此推定程式已符合規劃或正確運作；實作後須依上述真實接線驗收。除第 12 節產品決策外，已找到的規劃缺口均有明確批次與可執行驗收對應，未發現其他已證實但未列入的缺口。

## 12. 複查後仍需定案的產品邊界

**Q01：沒有新主機身分與核准計畫時，是否要求立即產生可保存資料的獨立備份？**

- 現行核心有明確限制：Export-WsmMigrationPackage 依賴 sealed migration plan；Approve-WsmMigrationPlan 需要真實 TargetIdentity，manifest 綁定目標。只加精靈不能提供不依賴目標的備份。不能用假目標身分、假核准或先顯示成功來補洞。
- 建議依已定案「沿用現有核心及核准」維持搬移用途：零準備時可先掃描／選取，開始備份前由工具帶著完成必要的目標／管理準備；已有有效材料則自動帶入並執行。介面應稱「自動備份已準備好的搬移內容」，啟動前列出必要交接，不暗示單靠舊主機能無條件完成。
- 若使用者要「只有舊主機也能備份」，需新增獨立來源備份材料及後續綁定目標的契約，連同來源授權、非 C 收集、材料信任、後續轉搬移包、版本相容、恢復及驗收一起規劃。它仍可不包含整機／OS／軟體本體，但不是原 E 的介面編排小修。
- 2026-10-12 使用者接續授權開始實作；本輪採上述沿用既有核心的建議，零準備時先掃描並導引管理／目標準備，不能產生獨立來源备份。此範圍已於開始實作時告知使用者。
