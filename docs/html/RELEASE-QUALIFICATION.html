Qualification and enterprise release gate

Status: Blocked / NotTested for production. This repository does not contain a trusted enterprise certificate, signed qualification evidence, production Server/Oracle results, or an approved enterprise release policy. ProductionExecutionEnabled remains false. A hash, evidence reference, self-entered owner, fixture, or release archive alone cannot authorize production.

Exact qualification scope

Qualification keys bind the exact tool and adapter fingerprints, source and target family/version/build/edition/architecture, source and target InstallationType, product and product version. Older tuples without InstallationType retain their old lookup key for compatibility, but they cannot qualify production. A Server Core result does not apply to Server with Desktop Experience, and a different build or adapter byte fingerprint is a different qualification.

When an Oracle provider is in scope, both OracleProvider and OracleConsumer are required. Each contains Product, Version, Architecture, and Context. The provider context identifies the Oracle Home and relevant client identity; the consumer context identifies the actual application/service/IIS/task runtime that loads it. A client qualification does not qualify a consumer, another provider version, architecture, Oracle Home, or consumer context. Database/listener business proof remains a separate, externally performed acceptance gate.

Enterprise trust contract

Production records must be created through New-WsmQualificationSigningRequest. The exact canonical bytes it writes are the approval subject. An independent QualificationApprover signs those bytes as a detached CMS/PKCS#7 signature. Complete-WsmQualificationSigningRequest accepts the request and signature only when both independently supplied hashes match, the signature verifies, the signer thumbprint and chain root are pinned for the QualificationApprover role in an unexpired enterprise trust policy, and pre-provisioned offline certificate/CRL status is present and current. CMS digests are limited to SHA-256/384/512; signer certificates must authorize digital signatures and use RSA-2048+ or ECDSA-256+. Windows PowerShell 5.1 uses Crypt32 with cache-only URL retrieval, cache-only revocation, root-excluded revocation checking, and AIA disabled. Newer runtimes set DisableCertificateDownloads and use offline revocation mode. Neither path initiates OCSP/CRL/AIA network lookup. Qualification records retain the detached signature and the exact signed projection hash. Add-WsmQualification, Resolve-WsmProductionQualification, and the matrix re-check current policy, signer/root authorization, revocation, evidence expiry, and the signed bytes. Missing trust policy, unavailable or stale offline revocation material, unsupported offline chain construction, untrusted/revoked/expired certificates, changed policy pins, changed signed content, or changed evidence hashes block qualification.

The Crypt32 path is implemented for Windows PowerShell 5.1, but local validation covers only a generated untrusted leaf rejection and flag selection. No enterprise chain with pre-provisioned revocation data was available for a positive native-chain test; that runtime remains Blocked/NotTested for formal production qualification.

EnterpriseTrustPolicy must be deployed by a separate enterprise administrator through a protected channel. Supply its path and independently obtained SHA256 to every qualification/release verification call. It contains a bounded UTC expiry, role rows named QualificationApprover and ReleaseSigner, the exact allowed signer and root thumbprints for each role, RevokedThumbprints, RevocationEvidenceUpdatedUtc, and RevocationMaxAgeHours (1–720). The expected policy hash must come from the administrator's trusted deployment record; storing a hash beside the policy does not make it trustworthy. The policy file itself must have restrictive ACLs and change control. Windows must trust the pinned certificate chain and have current CRL/certificate data provisioned locally before verification. Stale/missing local revocation material blocks. There is no self-enrollment or owner-entered trust shortcut.

Revoke a qualification with Revoke-WsmQualification; revocation is append-only and immediate for subsequent lookups. To rotate or revoke a signer, update the independently deployed policy and its trusted hash. A changed signer policy requires a new qualification approval. All evidence must be current at lookup; renewal produces a new signed record. Owner, Reference, and SHA256 fields describe reviewed evidence and bind exact bytes, but do not establish who produced or approved those bytes. The independent enterprise signature establishes reviewer authorization; underlying ServerLab, isolated-pilot, and ProductionAcceptance work must still be real and independently audited.

Example approval flow: first export and have the enterprise ReleaseSigner sign the final archive, then set $releaseCheck from Test-WsmToolRelease using independently supplied hashes and policy. The qualification tuple must contain that returned release metadata before it is signed. The signing command is supplied and controlled by the enterprise PKI team:

$tuple | Add-Member NoteProperty ReleaseArtifact ([pscustomobject]@{ArchiveSHA256=$releaseCheck.ArchiveSHA256;SignatureSHA256=$releaseCheck.SignatureSHA256;ToolFingerprint=$releaseCheck.ToolFingerprint;SignerThumbprint=$releaseCheck.SignerThumbprint;TrustPolicyHash=$releaseCheck.TrustPolicyHash}) -Force
$request = New-WsmQualificationSigningRequest -Tuple $tuple -Requirements $requirements -Evidence $evidence -CreatedBy 'release coordinator' -Path .\qualification-request.json
# Transfer the request bytes to the independent approver. They sign the exact file and return a detached CMS signature.
$record = Complete-WsmQualificationSigningRequest -RequestPath .\qualification-request.json -RequestHash $request.SHA256 -SignaturePath .\qualification-request.p7s -SignatureHash '<independently supplied qualification signature SHA256>' -ReleasePath .\tool-release.zip -ReleaseHash $releaseCheck.ArchiveSHA256 -ReleaseSignaturePath .\tool-release.p7s -ReleaseSignatureHash $releaseCheck.SignatureSHA256 -TrustPolicyPath .\enterprise-trust.json -TrustPolicyHash '<independently supplied policy SHA256>'
Add-WsmQualification -Path .\qualification-registry.json -Record $record -TrustPolicyPath .\enterprise-trust.json -TrustPolicyHash '<independently supplied policy SHA256>'

Do not put private keys, credentials, connection strings, or unredacted host settings in the repository, qualification registry, package, or support bundle.

Release package and byte trust

Export-WsmToolRelease creates a ZIP with a release.json file manifest, final tool fingerprint, payload sizes and SHA256 values, runtime declaration, and component summary. The archive includes the release notes, support matrix, recovery runbook, qualification policy, and machine-readable SBOM. Export is unsigned and always reports ProductionVerified=false.

Markdown documentation under docs, including docs/archive, retains its directory structure in the release so offline links to historical evidence still resolve. Archived plans and reviews are historical records; their inclusion does not establish current implementation or production qualification.

After all release files are frozen, have the enterprise ReleaseSigner sign the exact final ZIP bytes as detached CMS. Distribute the ZIP, detached signature, archive SHA256, signature SHA256, and trust-policy SHA256 over separate trusted channels. Run Test-WsmToolRelease -Path ... -ExpectedHash ... -SignaturePath ... -ExpectedSignatureHash ... -TrustPolicyPath ... -TrustPolicyHash ... on the receiving host. It validates ZIP entry names, duplicate/extra entries, size limits, compression ratio, per-entry hashes, the final tool fingerprint, expected archive/signature hashes, pinned ReleaseSigner/root policy, offline certificate chain and current cached CRL. No certificate or revocation network lookup is initiated. Any signed-byte change requires a new archive signature and new plan/qualification. Do not replace files after verification or while an operation is active.

The SBOM lists bundled and host-provided components; the manifest's per-file hashes are integrity evidence, not software-supplier certification. The archive is not encrypted. Use an enterprise-approved encrypted transfer/storage channel when confidentiality is required.

Host and operational constraints

  • Use 64-bit Windows PowerShell 5.1 in FullLanguage; run elevated only for the reviewed adapter operations that require it. The tool does not change execution policy, AppLocker, WDAC, UAC, or enterprise policy.
  • The host supplies .NET Framework and any OS roles/modules used by an adapter. The release does not bundle runtime installers or install Windows Features. Validate exact host roles, patch/build, adapter privileges, and native dependencies during isolated qualification.
  • Production qualification covers only the exact tuple recorded. Unknown OS installation types, provider/consumer contexts, unsupported adapters, failed or missing evidence, and untested scale remain NotTested/Blocked.
  • No real migration, source/target connection, Oracle DB test, production write, identity handoff, or retirement was performed for this release package. Production activation remains disabled.

Change approval and rollback boundary

Before any real cutover, obtain separate enterprise change approval that names the exact signed archive hash, tool fingerprint, qualification key, source/target identities, scope, maintenance window, owners, freeze/fencing plan, business acceptance criteria, backup/restore evidence, and rollback authority. Store the signed approval and its trusted reference outside the migration package; revalidate it at the enterprise change gate. Qualification is a support statement, not a cutover command. Never use a qualification record to turn on the production execution switch.

For operational recovery, follow RECOVERY-RUNBOOK.md. Preserve the operation state, journal, package, backup, transport, import, and target readback evidence before attempting repair or rollback. Stop on drift and obtain owner approval; do not infer rollback safety from a successful command exit.

執行引擎也屬於 exact tuple

新正式資格的 Tuple.Runtime 必須包含 Source 與 Target；每台各記 PowerShellVersion、Edition、ProcessArchitecture、LanguageMode、CLRVersion、DotNetFrameworkRelease。Get-WsmQualificationRuntime 可在本機輸出實際觀察，LabReport 的 Runtime 同步保留。支援政策目前限 Windows PowerShell 5.1 Desktop x64 FullLanguage；版本與 .NET Framework servicing release 一併納入 key，不能以 PowerShell 7 fixture 通過冒充 5.1 原生資格。

舊 tuple 的既有 lookup key 保持不變；缺 Runtime 的舊正式紀錄只可查閱，不能放行新的 production 資格。新簽章請求若缺任一端 Runtime、使用未知 framework release 或不符支援政策，會在寫入前拒絕。伺服器 runtime 漂移需取得該精確維度的新資格；manager 執行引擎不代替來源／目標引擎。

離線憑證鏈與演算法限制

Windows 使用 Crypt32，固定開啟 URL cache-only、停用 AIA、停用自動根憑證更新、chain-exclude-root revocation 與 revocation cache-only。企業根、intermediate 及有效 CRL 必須由受控外部程序預備，工具不在驗證過程下載。旗標含 CERT_CHAIN_DISABLE_AUTH_ROOT_AUTO_UPDATE，依 Microsoft CertGetCertificateChain。任何 combined/simple/element trust error、替代鏈或不精確 root pin 都拒絕。

簽章摘要只接受 SHA256／384／512；RSA 至少 2048 位、ECDSA 至少 256 位。鏈中每張憑證的簽章必須是 RSA PKCS#1 或 ECDSA 的 SHA256／384／512；其他演算法（含目前未受驗的 RSA-PSS）拒絕。葉憑證另需 DigitalSignature key usage。真實生成的強／弱 RSA 憑證與 detached CMS 已用於本機驗證演算法及不可信鏈拒絕路徑；沒有企業有效完整鏈／CRL 的正向實機結果，不能聲稱 PKI 放行已驗收。

資格撤銷權威來源

ProductionAccepted 驗證必須在獨立取得 SHA256 的 EnterpriseTrustPolicy 內包含 QualificationRevocations（可為空陣列）。每筆為 {QualificationId,Owner,Reference,RevokedUtc}，最多10,000筆，不得重複或使用未來時間。驗證每次重讀可信 policy；被列入即拒絕，直接刪除本機 QualificationRegistry 的 revocation 不能解除企業撤銷。

Revoke-WsmQualification 只增加本機拒絕紀錄，回傳 RevocationScope=LocalRegistryOnly 及 EnterpriseRevocationRequired=true；企業管理者仍須發佈含該 QualificationId 的新 policy，從受控部署紀錄提供新 hash。更換 policy hash 後，舊資格會 fail closed，須依 existing policy-hash binding 重新簽署與核准。不能自行從本機 policy 文件計算 hash 當作企業最新 policy 的授權。工具不提供企業 policy 發布、反回放時鐘或撤銷服務；最新 hash 與部署控制由企業獨立流程供給。
